# 评测-02：真机端侧验证报告（一加 Ace 2 / Termux + llama.cpp，PC 对比）

> 日期：2026-10-23 ｜ 方案 B（真机链路）执行完毕
> 设备：一加 Ace 2（PHK110，骁龙 8+ Gen1，16GB，Android 16）｜ 设备端：Termux v0.118.3 + llama.cpp b11669 android-arm64 + Qwen3-1.7B Q8_0（与 PC 端**同一模型文件、同一量化、同一版本 llama.cpp**）
> 对照组：同日 PC 端结果（`评测-01-Qwen3-1.7B首轮四子集结果.md`）

## 一、真机链路搭建记录（含三个环境坑）

1. **部署路径**：llama.cpp android-arm64 通用版（277MB）与模型（1.83GB）经 adb push 到
   `/sdcard/llama/`，Termux 中拷至 `~/llama/`（/sdcard 无执行权限）后直接运行，
   服务参数与 PC 端一致（8192 上下文、关思考模式、temperature=0），仅 `--host 0.0.0.0`
   走局域网、`-t 6` 留 2 核给系统。
2. **坑 1（仓库文档 bug）**：`harness/adapter_openai.py` docstring 写"Termux + llama-server
   用 `adb reverse` 后 PC 直连"——**方向是反的**。reverse 会让 adbd 占住设备端口，
   Termux 绑同一端口直接 `couldn't bind`。"PC 客户端 → 设备服务"必须用 `adb forward`。
3. **坑 2（本环境限制）**：adb server 进程在本环境**每条命令结束后即死**，forward/reverse
   全部清空，隧道活不过命令边界——长任务不可依赖 adb 隧道。
4. **坑 3（MSYS 路径改写）**：Git Bash 会把 `/sdcard/...` 参数改写成
   `D:/.../PortableGit/sdcard/...`，adb push 静默失败——须先 `export MSYS_NO_PATHCONV=1`。
5. **最终方案：局域网直连**。手机 WLAN `192.168.104.33`，PC `192.168.110.90`（同一 /20），
   harness 以 `--endpoint http://192.168.104.33:8081/v1` 访问。模型加载约 5 秒。
6. **版本提示**：b11669 起 `--chat-template-kwargs '{"enable_thinking":false}'` 已弃用
   （有警告但可用），新写法 `--reasoning off`。

## 三、性能与稳定性

| 子集 | PC 耗时 | 真机耗时 | 倍数 | 真机单条 |
|---|---|---|---|---|
| intent（1 次生成/条） | 3m26s | 7m20s | **2.1×** | 2.5s |
| faq（3 次生成/条） | ~2m | 15m17s | **~7×** | 10s |
| tool（~3 次生成/条） | ~1m | 3m27s | ~3.5× | 7s |
| mask（1 次生成/条，输出长） | ~7m | 27m05s | **3.9×** | 10.2s |

**结论 2：速度代价 2–7 倍，且与"单次问答的生成轮数"成正比**——这是 harness 架构的直接推论：
端侧一次用户交互 = 脱敏 + 分类 + 分支生成（FAQ 还要知识卡总结），三轮串行生成在手机上就是
10 秒级。多轮工具调用场景（本就没跑通）会再放大。**PC 驱动的评测架构在这件事上价值明显：
457 条真机评测 53 分钟跑完，harness 一行未改。**

**稳定性**：真机 intent 出现 8/176（4.5%）传输错误（6× HTTP 502 + 2× 连接中断），
局域网直连的偶发抖动；faq/mask/tool 仅 0–1 次。生产化评测建议走 USB（adb forward），
但本环境 adb 服务不稳定，属环境限制而非方案缺陷。

**未测项**：内存峰值、温度、掉电（bench/ 脚本面向常驻 CLI 设计，HTTP 服务形态需调整
perf_probe 的 pid 获取方式后补测）——留待 MNN 真机链路（D2）或专项性能轮次。

## 四、总结论

1. **"端侧部署伤不伤能力"——不伤。** 1.7B 在手机上的能力边界与 PC 完全一致：
   intent 0.82 / FAQ 0.46 / tool 0.1–0.2 / mask 0.89，全部低于预设阈值；
2. **"端侧部署伤什么"——伤速度。** 单问 2.5–10s，全链路问答约 10s 级，可接受但无余量；
   4B 模型的端侧速度预计再翻倍，是选型的关键约束；
3. **harness 的 PC 驱动 + 设备推理架构验证有效**：换后端只改一个 `--endpoint` 参数，
   四子集 + 四判分器全链路复用，457 条真机数据零代码改动；
4. **下一步优先级不变**：① taxonomy 相邻类修复（回收 intent 缺口）；② 4B-2507 对比
   （tool/FAQ 缺口大概率只有 4B 能补，且需评估端侧速度代价）；③ MNN D2 交叉编译
   （等 Docker 就位）对比 MNN 与 llama.cpp 的端侧性能差。

## 五、复现命令

```bash
# 设备端（Termux，~/llama 为拷入的二进制目录）
cd ~/llama && LD_LIBRARY_PATH=$HOME/llama ./llama-server \
  -m ~/storage/shared/llama/models/Qwen3-1.7B-Q8_0.gguf \
  -c 8192 --port 8081 --host 0.0.0.0 -fa on --reasoning off -t 6
# PC 侧评测（endpoint 换成设备 IP 即可，harness 零改动）
python eval/run_eval.py --backend openai --endpoint http://192.168.104.33:8081/v1 --subset <intent|faq|tool|mask>
```

> **安全收尾**：设备端服务绑定 `0.0.0.0` 且无鉴权，评测结束后应在 Termux `Ctrl+C` 停掉
> （或改回 `--host 127.0.0.1`）。本次会话结束时已提醒用户执行。
